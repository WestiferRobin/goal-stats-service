## Migration policy

The unchanged original revision `a7c93e25d104` remains the parent of the single
new forward revision `c8d42f19e630_retire_item_action.py`.

Upgrade acquires PostgreSQL ACCESS EXCLUSIVE locks on both `items` and `actions`
before inspecting either table. Both locks remain held through the guard, drops,
and Alembic revision update. A PostgreSQL DO block checks both tables and raises
`check_violation` with a clear retirement-refused message if either contains rows.
The transaction rolls back on failure; no legacy records are deleted. Empty tables
are dropped actions-first, without DROP CASCADE. Unexpected dependencies cause a
transactional failure rather than broad deletion. Stop old writers before rollout.

The guard is emitted as executable PostgreSQL SQL, so online upgrades and offline
`alembic upgrade head --sql` use the same checks. The maintained fresh SQL export
is generated by `scripts/database/export_football_sql.py --mode schema`; it applies
the complete chain and ends with eight tables and the new head. It is only for an
empty database, not an upgrade shortcut. Historical verification SQL checks the new
head. Prototype SQL remains unchanged.

Downgrade recreates **empty** Item/Action tables using the exact original column,
constraint, FK and index definitions. It cannot recover data. No persistent
upgrade, downgrade, restamp, or seed operation is performed in this phase.
